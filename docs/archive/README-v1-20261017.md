## 架构一句话

微信跑在 WSL 的 Xvfb 虚拟屏 :99 里，noVNC(localhost:6080) 提供可视化，
常驻服务 wechat-bot 在后台轮询会话、本地 OCR 判断，**只有要写内容时才调模型**。

    WSL Ubuntu-24.04
     ├─ Xvfb :99 (虚拟屏) ← 微信 4.1.1.8
     ├─ x11vnc :5900 ← websockify+noVNC :6080  (浏览器 http://localhost:6080/vnc.html)
     └─ wechat-bot.service
          · 多会话轮询(本地OCR)      · 分级优先级队列
          · 共用额度池               · 分会话记忆/自学习
          · 朋友圈发布+互动管道       · RSSHub 热榜

## 核心机制

- **零额度监控**：轮询/切换/截图/OCR/指纹对比全本地；只有回复、学习、朋友圈草稿、
  互动决策才花 API（一次1单位）
- **分级优先级**：群@(0) > 私信(1) > 群普通(2)，共用额度池排队串行发送
- **撞限额**：@/私信自动发「小年糕正在休息…请等待：XX分钟」→任务进等待队列→
  额度恢复自动继续
- **安全**：所有模型输出过 moments_safe 黑名单；学习到的内容标注不可信数据防注入
- **防发错窗**：每次发送前强制切换到目标会话并 OCR 核验标题
- **配置一致性警告**：watch_chats 里的群若不在 group_whitelist，status 会显式警告（不会被静默跳过）

| interact.comment_max | 60 | 单条评论最长字符（超出截断/拒写） |
| interact.whitelist_only | true | 只互动名单内好友的动态；决策官每条带 in_whitelist 标记 |
| interact.friends | [] | **好友昵称名单**（与朋友圈显示名一致，normalize 后比较）。whitelist_only=true 但名单为空 → fail-closed：零模型调用、不互动，status 记 interact_blocked_no_friends |
| interact.auto_execute | false | 是否免人工确认直接互动（保持 false，评论必须人审） |

填写示例：

    "interact": {
      "enabled": false,
      "batch_size": 8,
      "comment_max": 60,
      "whitelist_only": true,
      "friends": ["很帅的年糕", "某某某"],
      "auto_execute": false
    }

## 协作式 UI 互斥（第 46 轮）

- 同一状态目录内 wechat-ui.lock 使用内核 flock 跨进程排他，同线程嵌套可重入；文件保留、权限 600，不能删除锁文件来解锁。进程退出由内核释放锁，不按超时抢占。
- 常驻整个 cycle、MomentRelease 发布/开面板和互动 CLI 的真执行共用该锁。忙碌时常驻写 ui_busy 跳过；互动 CLI 返回 7、不会创建尝试记录；发布返回 ReleaseError，不碰 UI。
- 锁覆盖网络等待期间以防 UI 被其他协作流程改动，因此慢模型可能让其他 UI 任务暂时等候。它不约束用户手动操作、外部脚本或不同状态目录的实例，也不取代发送前标题/授权核验。
- 回归覆盖重入、线程竞争、异常释放及三个入口忙碌拒绝；另在临时目录做了真实 fork 跨进程验收，未操作微信。

## 轮询健康状态（第 45 轮）

状态快照包含 poll_health：逐会话 title_verified、observed、state、baseline_ready、baseline_count。切换失败、渲染不稳定、观察异常会保留为 poll_degraded；等待画面稳定为 poll_waiting，只有本轮全部会话确实观察到才是 polled。后续队列/学习状态继续携带最近一次 poll_health，并以 checked_at 区分新旧证据。该字段不证明消息已发送。

## 朋友圈发布入口修正（第 44 轮，离线验证）

- 修复“只准备编辑页却写 PUBLISHED”的接线错误：人审发布入口现在调用 publish_now，成功测试必须证明点过 Post；仅编辑就绪不得记发布成功。此前成功测试反而要求不点 Post，是错误验收口径。
- 人审令牌绑定草稿 id/话题/素材/正文/配图路径及图文件 SHA-256；改文案或同路径换图都会失效。旧版只含 id 的令牌失效。
- STOP、撤回批准、内容变化均会在提交前重新核验；没有状态回写器时在任何 UI 操作前拒绝。要求图文发布时缺图拒绝。
- 点 Post 前排他创建并 fsync PUBLISH_ATTEMPT；提交不确定则保留，阻止重发；完成状态回写后才移除占位。readiness 会显示该占位是否存在，人工恢复工具尚未提供。

## 互动执行授权（第 39 轮离线验证）

- 人审令牌绑定作者、原动态、评论、指纹及点赞/评论动作；旧版仅含 id 的令牌失效，内容或动作改变须重新确认。只点赞/只评论时，批准与执行须使用相同的 --no-comment/--no-like 参数。
- CLI 执行及关键动作前重读磁盘配置/令牌：STOP、关闭互动、撤回批准、移出好友名单均拒绝；名单为空或格式异常同样拒绝。CLI 始终要求好友名单，不以模型判断代替授权。
- 同一账本必须已有 PUBLISHED 且带发布时间的朋友圈记录；仅草稿或缺表不算发布链路成功。原动态和评论再次过关键词安全闸。
- 批量决策对非白名单作者和敏感原文作确定性拦截；评论家返回未选中 id 不得晋级 READY。
- 互动 CLI 在任何 UI 操作前，以 SQLite 事务提交 STARTED 尝试记录；同一动态 id 和指纹不可重复尝试，全账本同一时刻只准一个 STARTED/UNCERTAIN。成功与收件箱 DONE 同事务提交；异常标记 UNCERTAIN，进程被杀则 STARTED 留存。两者都阻止后续互动，不按超时解锁；--list 会列出 blocked_attempts。
- 这是保守的“至多尝试一次”防重，不是成功后自动续跑：任何占位后失败（包括尚未真正点击）都需要人工核对。不能通过重新批准、重置收件箱 READY 或删除暂停文件绕过；不要手工删除尝试记录来重跑。人工核对/恢复工具尚待实现。
- 朋友圈滚动使用当前截图尺寸内点，并在每次动作前重读窗口原点；显式越界坐标或异常小窗口拒绝滚动，修复旧 x=640 超出 573 像素窗口的问题。此边界检查不等于遮挡/焦点/并发 UI 安全证明。
- 定位不再接受作者子串：CLI 把已批准的原动态正文传给发布器，作者和完整正文去空白后均须精确匹配；正文至少 8 字，纯图片/短文/省略文本拒绝。当前画面出现多个 ··· 按钮时因卡片边界不可靠而拒绝；识别后整窗截图变化也拒绝，OCR 换行不影响正文匹配。
- **仍不可据此开启无人值守互动**：这是保守的文本绑定，不是动态唯一 ID。相同作者重复发布完全相同正文仍无法区分；卡片裁剪/滚动及真实 OCR 还需实机核验。支持多卡片/纯图片需要额外视觉证据，不能放宽成子串匹配。实机点赞/评论回执仍待验收；第 46 轮共享协作锁已覆盖常驻、发布与互动入口，但不约束未接入锁的脚本或用户手动操作。屏幕变化尚不能充分证明互动成功。

## 安全边界（写死的）

- 不读聊天数据库、不 hook、不注入（纯 UI）
- 朋友圈内容/评论不用热搜（公开平台风险不可控），只走白名单选题池
- 朋友圈发布没有"自动"开关可开：只有 APPROVE_MOMENT 令牌在位且坐标已标定才会发布，
  令牌由年糕手动 --approve 生成，可随时 --revoke；互动默认 enabled:false
- 凭证只在 WSL 私有目录 ~/.local/state/wechat-bot/credentials.json（600 权限）
